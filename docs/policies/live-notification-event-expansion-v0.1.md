# LIVE Notification Event Expansion v0.1

## Purpose and scope

Internal validation fixtures lock down the existing LIVE-candidate pipeline for
three additional events. This does not activate them in Scheduler or change any
Runtime, Adapter, Sender or Bridge policy. The fixture module has no imports,
delivery API, executable CLI, credentials or I/O. Its only function returns a fresh
synthetic exact nine-field event from a three-name allowlist; all other inputs fail
with a fixed safe error. There are no field, identity, priority or path overrides.

## Event matrix (existing Adapter policy)

| Event | Priority | Delivery class | Validation role |
|---|---:|---|---|
| JOB_FAILED_SAFE | 1 | IMMEDIATE | New synthetic validation fixture |
| QUEUE_BLOCKED | 1 | IMMEDIATE | New synthetic validation fixture |
| JOB_COMPLETED | 0 | NORMAL | New synthetic validation fixture |
| JOB_WAITING_APPROVAL | 1 | IMMEDIATE | Existing dedicated Scheduler canary; unchanged |

The three new fixtures have approval_required=false. Their respective severity /
state pairs are ERROR/FAILED_SAFE, WARN/BLOCKED and INFO/DONE. Shared synthetic
job_id=notification-expansion-fixture-v0.1, job_type=notification_validation,
summary_code=NOTIFICATION_EXPANSION_FIXTURE_V01 and fixed occurred_at=
2026-08-27T00:00:00Z are identity inputs, not actual job or delivery facts.
Runtime alone computes its existing SHA-256 identity; no digest logic is copied.
Identities are stable across calls/processes and distinct between event types,
including with an identical job_id. These fixtures are not persisted Queue jobs.

## Suppression and emergency exclusions

| Event | Priority | Existing treatment |
|---|---:|---|
| JOB_STARTED | -1 | SUPPRESSIBLE; Runtime suppresses |
| JOB_CHECKPOINTED | 0 | SUPPRESSIBLE; Runtime suppresses |
| JOB_SWITCHED | 0 | SUPPRESSIBLE; Runtime suppresses |
| QUEUE_IDLE | -1 | SUPPRESSIBLE; Runtime suppresses |
| CRITICAL_STOP | 2 | Emergency candidate; EMERGENCY_SEND_BLOCKED, no LIVE send |

None of these five events can be generated by the expansion module. An existing
regression fixture verifies the emergency negative invariant without real transport.
The Scheduler Bridge remains JOB_WAITING_APPROVAL-only, not a general event CLI.
Its confirmation gate does not authenticate Task Scheduler as the caller.

## Delegation and Ledger semantics

Tests pass fixtures to the unchanged Runtime using an isolated temporary Ledger,
explicit fixture credentials and mock transport. Adapter creates the fixed title,
message, priority and class. Sender remains the sole transport boundary. Spies wrap
the real Adapter and Sender functions; no alternative delivery implementation is
introduced. Accidental real credential/transport fallback fails tests.

With a HEALTHY temporary snapshot, initial mock delivery adds one success record.
The identical next event is NOTIFICATION_DUPLICATE_SUPPRESSED before Adapter,
Sender or credential access; snapshot bytes remain unchanged. Rejected responses,
Sender exceptions, timeouts and delivery_succeeded=false add no success record.
No retries, cleanup or repair are started. Existing best-effort crash-window
limitations still apply. Runtime's existing HEALTHY requirement for LIVE remains.

## No state mutation and security

Failed-safe notification does not retry, rerun or repair jobs; blocked notification
does not unblock, switch jobs, create approvals or repair queues; completed
notification does not delete jobs/checkpoints or perform cleanup. No Queue,
Approval, DB, Temporal, Publication, Public Data, Lifecycle, Semantics or Official
Blocker write is performed. Real production Ledger stays read-only (one existing
approval-canary record); .env and credentials stay unchanged. Runtime safe outputs
contain no credential values, payloads, raw responses or notification text.

## Scheduler and activation prerequisites

All five existing task definitions remain unchanged. LIVE Task stays Disabled with
no trigger. No canary re-send, task enable, new LIVE CLI, recurring activation,
automatic event ingestion, approval automation, deployment or emergency send is
part of this work. Before any future real event test, obtain separate explicit
operator approval, capture protected-data/task snapshots, require HEALTHY, audit
a narrowly scoped event entrypoint and verify identity/deduplication. This pure
fixture helper is not such an entrypoint and does not authorize LIVE delivery.
